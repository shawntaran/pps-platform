# pps-privacy

The GDPR/DPDP privacy guardrail layer. Design and reasoning live in
[`docs/privacy/`](../../docs/privacy/); this README is just how to run it.

## What is here

| Path | What it does |
|---|---|
| `src/pps_privacy/crypto/envelope.py` | AES-256-GCM, with every ciphertext bound to its row and column |
| `src/pps_privacy/crypto/keyprovider.py` | Per-record data keys wrapped by KMS; local provider for dev |
| `src/pps_privacy/crypto/blind_index.py` | Equality lookup on encrypted email and phone columns |
| `migrations/` | The three-zone schema, roles, row-level security and grants |

## Setup

```bash
cd services/privacy
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -e ".[dev]"    # Windows
# .venv/bin/pip install -e ".[dev]"                      # macOS / Linux
```

## Tests

```bash
./.venv/Scripts/python.exe -m pytest -q
```

The crypto tests run anywhere. The schema tests need PostgreSQL 15+ and are
skipped without it:

```bash
docker compose -f docker-compose.dev.yml up -d
export PPS_TEST_DATABASE_URL=postgresql://pps:pps@localhost:5433/pps_test
./.venv/Scripts/python.exe -m pytest -q
```

That database runs on tmpfs and is wiped on every restart, which is deliberate:
a dev database should never quietly accumulate real student data.

## Migrations

```bash
export DATABASE_URL=postgresql+psycopg://pps:pps@localhost:5433/pps_test
./.venv/Scripts/python.exe -m alembic upgrade head

# Review what would run, without connecting to anything:
./.venv/Scripts/python.exe -m alembic upgrade head --sql
```

Migrations are hand-written SQL, not autogenerated from ORM models. The security
properties here live in GRANTs, RLS policies and append-only triggers, none of
which a model captures, and the SQL has to be reviewable by people checking our
compliance claims.

Creating roles needs `rds_superuser` on RDS, so run migrations as the
provisioning user, not as an application user.

## Configuration

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Migrations and the app. Read it from Secrets Manager in deployed environments |
| `PPS_TEST_DATABASE_URL` | Enables the schema tests. Point it at a throwaway database only |
| `PPS_ENV` | `production` makes `LocalKeyProvider` refuse to start |
| `PPS_MASTER_KEY` | Base64 master key for `LocalKeyProvider`. Dev and tests only |

Generate a dev master key:

```bash
python -c "import os,base64; print(base64.b64encode(os.urandom(32)).decode())"
```

No secret belongs in a committed file. The repository `.gitignore` covers
`.env`, key files and uploaded resumes, but it is a safety net, not permission
to be casual: anything that reaches git history is effectively permanent.

## Two things to know before changing this

**The analysis zone must not reference the identity zone.** No foreign keys, no
`user_id` column, no join. A trainer screen showing a name beside an ATS report
resolves the pseudonymous ID in the identity zone first and joins in application
memory. Adding `REFERENCES identity.users` to an analysis table would collapse
the separation the whole design rests on -- `test_analysis_tables_have_no_foreign_keys_into_identity`
exists to catch exactly that.

**Row-level security is the second line, not the first.** Every API route still
enforces authorisation itself. RLS means a missed check fails closed rather than
returning a student, and `app.actor_id` / `app.actor_role` must be set with
`SET LOCAL` from the verified session -- never from anything a caller supplies.
